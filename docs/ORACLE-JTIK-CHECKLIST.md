# Checklist teknikal Oracle untuk JTIK

Keputusan makmal menggunakan Oracle Free 23.26.4. JTIK perlu meluluskan PDB terasing untuk pengesahan pada Oracle Database 19.30 Standard Edition 2. Pengaktifan rasmi memerlukan penerimaan teknikal dan proses berasingan. [Matriks P0](ORACLE-DELEGATION-P0-MATRIX.md) · [Serahan Team 2](ORACLE-TEAM2-HANDOVER.md)

| Semakan JTIK | Bukti sebelum kelulusan |
| --- | --- |
| Edition, patch dan PDB | Rekod `V$VERSION`, `DBA_REGISTRY_SQLPATCH`, nama/service/PDB, versi klien dan direktori log. Sahkan 19.30 SE2 serta PDB ujian terasing. Uji bahawa proses gagal tertutup untuk service, schema atau versi tidak sepadan. |
| Ruang nama INDECS | Bandingkan senarai semua objek `STL_` dalam inventori 001–003 dengan objek sedia ada sebelum DDL. Bandingkan checksum, definisi indeks dan keadaan kekangan/triggers selepas pasang. Sahkan semua objek sah dan tiada konflik dengan aplikasi lain. |
| Akaun dan grants | Semak matriks owner pemasangan, principal API, worker pengimbasan, audit baca dan operasi pemulihan. Hadkan API daripada lajur verdict, worker daripada kuasa pengesahan serta kedua-duanya daripada DDL dan skema jiran. Uji penolakan akses tersebut dengan akaun sebenar staging. Gunakan grant lajur dan elakkan grant melalui PUBLIC. |
| Pengecualian LOB | Sahkan `SYS_IL` ialah indeks dalaman janaan Oracle hanya melalui padanan `USER_LOBS` dan `USER_INDEXES` ke jadual dan segmen `STL_`. Bukti Free menunjukkan 14 entri. Rekod keputusan JTIK tentang pengecualian nama sistem ini. |
| Kapasiti | Tetapkan bajet tablespace bagi BLOB/CLOB, kuota `STL_`, Undo, Temp, redo dan ruang arkib. Ukur profil dokumen, retensi, versi/supersession dan kadar pertumbuhan. Tetapkan batas pool, beban scanner, panjang antrean, kadar imbas dan had 20 MiB atau ambang yang diluluskan. |
| Prestasi dan transaksi | Jalankan beban campuran dengan aplikasi INDECS lain. Rekod p50/p95/p99, kadar timeout, penggunaan pool dan lock wait. Semak pelan untuk giliran reviu, JSON_VALUE, indeks audit, pemilihan imbas dan FK. Uji pembatalan proses, kes commit tidak pasti, ulangan pembayaran, penggantian versi, tuntutan worker serentak dan kehilangan sambungan. |
| Backup dan restore | Tetapkan RPO/RTO dan jalankan RMAN serta kaedah logik yang dipersetujui pada PDB staging. Sahkan objek, grant, versi schema, hash sampel BLOB, padanan FK, bukti kuarantin dan peristiwa Issue #68 selepas pulih. Uji pemulihan kunci, konfigurasi, stor fail luar dan rekod sistem berasingan. |
| Migrasi dan rollback | Simpan backup disahkan sebelum 003. Rekod `APPLYING` dan hentikan langkah selepas kegagalan DDL. Semak `recovery.ts` sebelum pemulihan atau pembaikan oleh DBA. Pulihkan snapshot pra-003 kepada skema dengan 001/002 dulu, kemudian naik taraf salinan. Jika binari pra-P0 digunakan sementara, tutup kedua-dua laluan muat turun serta verifikasi sebelum dihidupkan. |
| Scanner, proksi dan audit | Sahkan sambungan scanner terurus, had strim, timeout, semakan verdict, stor persendirian dan log audit minimum. Jalankan A-N05 melalui proksi staging dengan semakan cache dan redaksi. Team 3 menilai semula kedua-dua P0 pada satu SHA calon. |
| Cutover dan kelulusan | Bentangkan bukti versi, QA, load, pemulihan dan pelan rollback kepada JTIK, Team 3 dan pemilik proses. Jadualkan freeze, sandaran, semakan delta, pertukaran service dan titik keputusan undur. Gerbang rasmi kekal fail-closed sehingga semua kebergantungan diluluskan. |

## Pemasangan makmal 003

Sediakan akaun owner, runtime dan scanner yang berasingan. Jalankan `install.ts preflight` dan `install.ts apply` menggunakan fail env owner. Untuk `seed.ts`, aktifkan grant API yang digunakan dan tetapkan `ORACLE_LAB_DELEGATION_SCANNER_USER` kepada pengguna makmal scanner. Pengimbas Oracle memerlukan fail env akaun scanner, `NODE_ENV=test`, `STAYLINK_DELEGATION_SCAN_ENABLED=true` dan `STAYLINK_CLAMAV_ENABLED=true`. Gunakan `npm run oracle:delegations:scan` hanya dengan scanner makmal yang diluluskan. Ujian kesetaraan menggunakan fixture dan beroperasi tanpa ClamAV rasmi.

Pemasangan 003 mengekalkan checksum 001/002. Kolum scan asal meletakkan PDF lama dalam `LEGACY` dan lalai bagi kemasukan baharu Oracle ialah `PENDING`. Eksport logik menyimpan hash bagi data dan susunan kolum. Pemulihan 003 menangguhkan hanya FK bukti berkitar sepanjang sisipan, mengesahkannya sebelum komit dan menyemak semula checksum.

## Probe staging untuk scanner, TLS dan cache

- Sediakan endpoint ClamAV privat, versi signature yang direkodkan, timeout dan had strim mengikut had muat naik. Tetapkan `STAYLINK_CLAMAV_HOST`, `STAYLINK_CLAMAV_PORT`, `STAYLINK_CLAMAV_ENABLED=true` dan `STAYLINK_JTIK_SYNTHETIC_PROBE=true`. Jalankan `node --import tsx scripts/jtik/check-clamav.ts`. Skrip menjangka CLEAN bagi fixture PDF dan INFECTED bagi fail ujian standard EICAR. Kedua-dua fixture dihantar hanya kepada scanner yang dibenarkan.
- Gunakan TLS 1.2/1.3, sijil dipercayai, log akses tanpa query/header dan arahan `deploy/jtik/delegation-proxy.inc` pada lokasi API staging. Gunakan dua sesi sintetik dan satu PDF CLEAN. Sediakan fail JSON persendirian dengan `origin`, `documentId`, `ownerCookie`, `outsiderCookie`, `fixturePath` dan `accessLog`. Benarkan skrip membaca log staging dari permulaan probe. Jalankan `node --import tsx scripts/jtik/check-delegation-proxy.ts path.json` dengan opt-in yang sama. Gunakan `NODE_EXTRA_CA_CERTS` untuk CA staging. Skrip mengesahkan urutan 200/404/200, lampiran, bait, no-store dan redaksi log.
- Untuk preflight read-only, DBA boleh menjalankan `@scripts/jtik/oracle-readiness.sql` dalam PDB ujian. Rekod output menggunakan polisi log JTIK. Gunakan ukuran segmen, inventori dan sesi untuk menetapkan beban sasaran serta uji restore dan DR mengikut RPO/RTO sebelum cutover. Asingkan service, pemilik skema, akaun API, worker, scanner, kunci, stor dan log makmal daripada produksi.
